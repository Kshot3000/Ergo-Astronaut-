Ergo, in 30 seconds

  • eUTXO, not accounts. Ergo extends Bitcoin's UTXO model: funds live in boxes that can carry data and tokens, so contract logic is predictable and fees can be worked out before you ever submit.
  • ErgoScript + Sigma protocols. Contracts are written in ErgoScript and built on Sigma protocols — composable zero-knowledge proofs (prove this AND that, or any 2 of 3 signers) baked into the language itself.
  • Autolykos proof of work. Ergo is mined, not staked, using the memory-hard Autolykos algorithm. It launched fairly in 2019 — no ICO and no pre-mine sale.
  • Storage rent. Boxes untouched for about four years can be charged a small rent by miners. Lost coins slowly return to circulation and long-term state stays paid for.
  • Babel fees. No ERG for the fee? Babel fees let you pay a transaction fee in a native token instead, swapped through a special babel box — no detour to an exchange.
  • NIPoPoWs. Non-Interactive Proofs of Proof-of-Work compress the chain into a small, checkable proof, so light clients and other chains can verify Ergo's work without downloading everything.

1 · ERG ⇄ nanoERG converter

2 · Ergo address checker

Paste any Ergo address. I Base58-decode it locally, verify its real checksum — the first 4 bytes of Blake2b-256 over the address bytes, stored as the last 4 bytes — and read its network and type byte. Try it with the donation address below.

3 · Storage rent estimator

Ergo charges rent on boxes left unspent for 1,051,200 blocks (about 4 years): the fee is the box's serialized size × the storage fee factor — currently 1,250,000 nanoERG per byte on mainnet, a votable chain parameter I verified against live network params. A simple ERG-only box is roughly 100 bytes serialized; boxes carrying tokens or register data are larger. Tokens cannot pay rent — only the box's ERG can.

4 · Autolykos mining-share estimator

What share of Ergo's blocks should your rig expect? Your expected share of blocks equals your share of the network's Autolykos hashrate, at Ergo's 2-minute block target (~720 blocks/day). You supply every figure — this tool fetches nothing and claims no live network data, and the block reward steps down over time, so read the current one off a block explorer.

5 · Minimum box value checker

Ergo rejects a box whose value is below its serialized size × the minimum value per byte — 360 nanoERG per byte, the rate set at launch and still the live mainnet parameter (a votable chain parameter I verified against live network params). A simple ERG-only box is roughly 100 bytes serialized; boxes carrying tokens or register data are larger. When the exact size is unknown, wallets use a recommended safe minimum of 0.001 ERG per box.

6 · Token amount converter (raw ⇄ display)

On-chain, Ergo token amounts are whole integers — no decimals. Each token's metadata declares its decimal places (ERG itself is the 9-decimal case from tool 1: nanoERG is the raw unit), and wallets divide the raw integer by 10decimals to show it. Enter the decimals exactly as the token's explorer listing shows them, then convert either way — exact BigInt maths, and a display amount smaller than one raw unit is rejected, because it cannot exist on-chain.

9 · UTXO payment planner (box selection + change)

Ergo spends boxes whole: to pay, a wallet selects input boxes until their total covers the payment plus the transaction fee, and the leftover comes back as a change box. 32 · Public key inspector (compressed key → the point behind it)

111 · Sigma (Schnorr) proof verifier (public key + commitment + challenge + response → does the proof equation hold?)

Tools 103 to 110 move public keys around; this tool checks the equation Ergo's signatures actually stand on. 69 · nBits ⇄ difficulty codec (the compact number every block header carries)

Every header the tools above inspect carries its difficulty as a 32-bit nBits — a compact float-like spelling: the top byte is a size (how many bytes the difficulty takes), the low 23 bits a mantissa, and the bit between them a sign, so the difficulty is mantissa × 256size−3, negated if the sign bit is set. Tools 62 and 68 decode it silently on the way through; this tool is that codec on its own, in both directions, ported from the reference node's DifficultySerializer. Decode takes an nBits in decimal or 0x-hex and gives the exact difficulty, the size and mantissa it came from, and the target b = q / difficulty (q the secp256k1 group order) that tool 68 compares a header's Autolykos hit against. Encode takes a difficulty and gives its nBits — and is honest about the format's limit: only the top three bytes survive, so a difficulty with anything in its lower bytes comes back smaller, and the tool says by how much rather than pretending the round trip is exact. A compact value whose sign bit is set decodes negative, and a zero mantissa decodes to zero — neither is a difficulty a node would accept in a header, and the tool flags both instead of dressing them up. Exact BigInt maths, verified against an independent Python port of the same reference code before it shipped here. Converting only: it fetches nothing, signs nothing and sends nothing.

70 · Next-epoch difficulty calculator (epoch-boundary blocks → the difficulty the next block must carry)

Ergo difficulty is not set per block: it holds for a whole epoch and is recalculated only for the epoch's first block, from the last blocks of the epochs behind it — and a block whose difficulty differs from what this calculation gives is invalid, however good its proof-of-work is. Paste those boundary blocks, one per line as height, timestamp (milliseconds), difficulty — tool 62 reads all three off any serialized header, and explorers list them per block. The calculator works out the rest from the chain's own rules. If the next block is mid-epoch it simply inherits its parent's difficulty, and that is the answer. At an epoch start the target interval is 120 seconds and the lookback is 8 epochs: each past epoch implies a classic adjustment (its difficulty × 120,000 ms × epoch length ÷ its actual duration), a least-squares line through those points extrapolates one epoch ahead, and before EIP-37 that prediction — round-tripped through the nBits of tool 69 — was the new difficulty over 1,024-block epochs. Since EIP-37 (height 844,673, 128-block epochs) the prediction is clamped into [last ÷ 2, last × 3/2], averaged with the classic adjustment of just the last epoch, clamped again, and only then normalized. The one exception is the Autolykos version-2 activation at height 417,792, whose difficulty the mainnet settings fix outright. This computes the difficulty a block must carry — arithmetic over the blocks you paste, not a forecast of hashrate or price. Calculating only: it fetches nothing, signs nothing and sends nothing.

71 · Block header votes decoder (serialized header → what its three miner-vote bytes actually propose)

Every header carries three miner-vote bytes — tool 62 shows them as raw hex and stops there. The ids: 1 storage fee factor, 2 minimum value per byte, 3 maximum block size, 4 maximum block cost, 5 token access cost, 6 input cost, 7 data input cost, 8 output cost, and 9 sub-blocks per block (added with block version 4). A miner casts at most two parameter votes per header; the third slot is where a soft-fork vote rides. Votes are tallied over 1,024-block voting epochs — a parameter change needs more than half an epoch's votes (at least 513), a soft-fork more than 90% across 32 epochs (at least 29,492 of 32,768) — so one header is one miner's ballot, and this tool decodes the ballot; it does not tally the epoch, and a vote cast is not a change approved. Paste both sets, one serialized transaction per line in each, and the remainder transactions come back: sorted by transaction ID, with the first set's bytes handed back in that order, ready to paste into tools 78 or 79. Sorting by transaction ID makes the remainder order a property of the set, never of paste order. Identity is the transaction ID, so a signed form on one side and the unsigned form on the other are the same transaction — removed, not remaining. Direction matters: the first set minus the second is a different question from the reverse, and every report says so. The remainder total output value, byte total and per-token totals are exact sums over the remainder transactions only, and they are tool 78's own totals for the remainder bytes — the remainder set is re-summarized by tool 78 itself before anything is shown, so the two tools can never disagree. The remainder set keeps tool 78's other judgement too: a box spent by more than one remainder transaction is a shared input inside the remainder set — what is left after the subtraction can still spend the same box twice, so at most one of them can ever confirm. Data inputs are only read, not spent, so they never count. A second set that covers the first is reported plainly as emptying it, with zero totals — an answer, not an error. Each side is a set in its own right, so a single transaction is a valid side; a transaction pasted twice inside one side — including its signed and unsigned forms, which share one ID — is refused, not counted twice. The honesty boundary is stated plainly: this subtracts the bytes you pasted — it fetches nothing, proves neither set is confirmed or broadcastable, and a remainder between two pasted sets proves neither is the chain's real state. Subtraction only: it fetches nothing, signs nothing and sends nothing.

Cross-chain: Ergo ⇄ Cardano, and the integration lab
