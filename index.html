Ergo, in 30 seconds

  • eUTXO, not accounts. Ergo extends Bitcoin's UTXO model: funds live in boxes that can carry data and tokens, so contract logic is predictable and fees can be worked out before you ever submit.
  • ErgoScript + Sigma protocols. Contracts are written in ErgoScript and built on Sigma protocols — composable zero-knowledge proofs (prove this AND that, or any 2 of 3 signers) baked into the language itself.
  • Autolykos proof of work. Ergo is mined, not staked, using the memory-hard Autolykos algorithm. It launched fairly in 2019 — no ICO and no pre-mine sale.
  • Storage rent. Boxes untouched for about four years can be charged a small rent by miners. Lost coins slowly return to circulation and long-term state stays paid for.
  • Babel fees. No ERG for the fee? Babel fees let you pay a transaction fee in a native token instead, swapped through a special babel box — no detour to an exchange.
  • NIPoPoWs. Non-Interactive Proofs of Proof-of-Work compress the chain into a small, checkable proof, so light clients and other chains can verify Ergo's work without downloading everything.

Flight tools — right here, nothing leaves your browser

1 · ERG ⇄ nanoERG converter

1 ERG is exactly 1,000,000,000 nanoERG. Fill in one side and convert — exact BigInt maths, no floating-point drift, done locally.

2 · Ergo address checker

Paste any Ergo address. I Base58-decode it locally, verify its real checksum — the first 4 bytes of Blake2b-256 over the address bytes, stored as the last 4 bytes — and read its network and type byte. Try it with the donation address below.

3 · Storage rent estimator

Ergo charges rent on boxes left unspent for 1,051,200 blocks (about 4 years): the fee is the box's serialized size × the storage fee factor — currently 1,250,000 nanoERG per byte on mainnet, a votable chain parameter I verified against live network params. A simple ERG-only box is roughly 100 bytes serialized; boxes carrying tokens or register data are larger. Tokens cannot pay rent — only the box's ERG can.

4 · Autolykos mining-share estimator

What share of Ergo's blocks should your rig expect? Your expected share of blocks equals your share of the network's Autolykos hashrate, at Ergo's 2-minute block target (~720 blocks/day). You supply every figure — this tool fetches nothing and claims no live network data, and the block reward steps down over time, so read the current one off a block explorer.

5 · Minimum box value checker

Ergo rejects a box whose value is below its serialized size × the minimum value per byte — 360 nanoERG per byte, the rate set at launch and still the live mainnet parameter (a votable chain parameter I verified against live network params). A simple ERG-only box is roughly 100 bytes serialized; boxes carrying tokens or register data are larger. When the exact size is unknown, wallets use a recommended safe minimum of 0.001 ERG per box.

6 · Token amount converter (raw ⇄ display)

On-chain, Ergo token amounts are whole integers — no decimals. Each token's metadata declares its decimal places (ERG itself is the 9-decimal case from tool 1: nanoERG is the raw unit), and wallets divide the raw integer by 10decimals to show it. Enter the decimals exactly as the token's explorer listing shows them, then convert either way — exact BigInt maths, and a display amount smaller than one raw unit is rejected, because it cannot exist on-chain.

7 · Storage rent countdown

When does a box's rent clock run out? A box becomes eligible for storage rent (tool 3) once the chain reaches its creation height + 1,051,200 blocks — about 4 years at the 2-minute block target. You supply both heights from a block explorer (a box's creation height is on its explorer page) — this tool fetches nothing and claims no live chain data.

8 · P2PK address builder (public key → address)

The other direction from tool 2: give me a compressed public key (33 bytes, 66 hex characters, starting 02 or 03) and I build its P2PK address locally — prefix byte for the network, your key, and the Blake2b-256 checksum over both, Base58-encoded, exactly as Ergo defines it. Public keys only — never type a private key or seed phrase into any website, this one included.

9 · UTXO payment planner (box selection + change)

Ergo spends boxes whole: to pay, a wallet selects input boxes until their total covers the payment plus the transaction fee, and the leftover comes back as a change box. List your boxes' ERG values in order and I walk them in that order — exact BigInt maths, done locally, nothing signed or sent. A leftover above zero but below the recommended 0.001 ERG safe minimum per box (tool 5) is dust, and the planner flags it: real wallets usually fold dust into the fee instead of creating a near-worthless change box.

10 · ErgoTree inspector (script hex → address)

Every box is guarded by an ErgoTree script, and its address commits to that script's proposition — the tree bytes after the header byte (and the VLQ size, when the header's size flag is set). Paste a box's ErgoTree hex from its explorer page and I read the header locally, spot the standard P2PK script and its key, and derive the script's P2SH address: the first 24 bytes of Blake2b-256 over the proposition bytes. Hashing the whole tree instead is the fleet-sdk bug I reported as issue #219 — it produced addresses whose boxes can never be spent. An ErgoTree carries no network, so pick the one you want the address for. Constant-segregated trees are reported honestly, not guessed at: their hash needs the constants substituted back in, which raw bytes alone cannot do.

11 · Address → ErgoTree decoder (what an address carries)

The reverse of tools 8 and 10: paste any Ergo address and I decode it locally — the network is read from the address itself, the checksum verified exactly as in tool 2 — and show what its content actually is. A P2PK address carries its 33-byte public key, so its ErgoTree (header 00 + the 08cd ProveDlog proposition + the key) comes straight back. A P2S address carries the script itself, so its content is its ErgoTree. A P2SH address carries only the 24-byte script hash, and a hash is one-way — the script cannot be recovered from it, so I show the hash and say so instead of inventing a script.

12 · Babel fee calculator (pay the fee in a token)

No ERG for the transaction fee? A babel box solves that: it is a box holding ERG whose contract lets you swap a native token for ERG at a stated price — the price sits in the box's R5 register, in nanoERG per raw token unit (read it off the box's explorer page). Enter the ERG amount you need, that price, and the token's decimals, and I work out the smallest whole number of raw tokens whose swap covers it — exact ceiling maths with BigInt, done locally. This tool fetches nothing and claims no live babel-box data.

13 · Address network converter (mainnet ⇄ testnet)

Testing a contract or an app and need the same address on the other network? An Ergo address is a prefix byte, its content, and a checksum (tool 2) — and only the prefix byte's high nibble carries the network: 0x0 mainnet, 0x1 testnet. The content is byte-for-byte identical on both networks, so I verify the checksum, swap the network nibble, and recompute the checksum over the new prefix. One warning that matters: the two networks are separate worlds — the converted address guards boxes on that network only, and sending mainnet ERG to a testnet address (or testnet ERG to a mainnet one) loses it.

14 · Box ID calculator (box bytes → box ID)

Every box has an ID, and it is not assigned or stored inside the box — it is derived: a box ID is the Blake2b-256 of the box's serialized bytes, meaning the full serialization (value, script, creation height, tokens and registers, followed by the creating transaction's ID and the box's index in it). Paste those full serialized bytes — SDKs and node APIs produce them, and explorers link them from a box's page — and I hash them locally and show the ID. Hashing only the candidate bytes gives a different value that is not the box ID. The same derivation names tokens: a token minted in a transaction takes the box ID of that transaction's first input as its token ID. Optionally paste an expected ID and I will tell you plainly whether the bytes match it.

15 · Serialized box parser (box bytes → every field)

The full read-back of tool 14: paste a box's full serialized bytes and I take them apart locally, field by field, in the exact layout Ergo serializes a box — the value (a VLQ integer), the ErgoTree, the creation height, each token's 32-byte ID and raw amount, the non-mandatory registers R4–R9 decoded as the Sigma constants they hold, then the creating transaction's ID and the box's output index — and I recompute the box ID from the same bytes, so it always agrees with tool 14. Two honest limits, the same ones fleet-sdk's own box deserializer has: a script with no size field that is not the standard P2PK tree or the miner fee contract cannot be delimited without parsing the full script, and a register holding an exotic constant type (an Option, Box or AvlTree constant) stops the parse — both are reported plainly rather than guessed past, because a wrong field boundary would silently corrupt every field after it. Integer registers decode at the same widths fleet-sdk's reader uses — Short and Int through its 32-bit zigzag, Long through its 64-bit one — so even an SInt sitting at a 32-bit extreme reads back as the value that was actually written.

16 · P2S address builder (ErgoTree → pay-to-script address)

The encode-side inverse of tool 11: a P2S address carries the script itself — its content is the full ErgoTree bytes verbatim, under a prefix byte (0x03 mainnet, 0x13 testnet) plus the Blake2b-256 checksum from tool 2, Base58-encoded. That is the opposite trade from P2SH in tool 10, which carries only the script's 24-byte hash: a P2S address is exactly as long as the script and reveals it to anyone who sees the address, while a P2SH address stays short and hides the script until a box is spent. Paste a script's ErgoTree hex — from tool 15's parser, an explorer, or tool 11 — and I parse it with tool 10's parser first, refuse anything that does not parse, build the address locally, and round-trip it through tool 11's decoder before showing it. P2S also carries constant-segregated trees exactly, the case tool 10 honestly declines to hash. Building an address proves nothing about who can spend a box it guards — that depends on the script itself.

17 · Serialized box builder (fields → box bytes + box ID)

The encode-side inverse of tool 15: give me a box's fields and I assemble its serialized bytes locally, in the exact layout Ergo writes a box — value as a VLQ integer, the ErgoTree verbatim, creation height, each token's 32-byte ID and raw amount, the non-mandatory registers R4–R9 as the Sigma constants they hold, then the creating transaction's ID and the output index — and I hash the result with tool 14's derivation to show the box ID. Registers are typed values, one per line in R4, R5, … order: bool:true, byte:-5, short:17, int:852574, long:430550309, bigint:1039, group:<66 hex chars>, dlog:<66 hex chars> (a ProveDlog SigmaProp), bytes:<hex> (a Coll[SByte]), ints:1,2,3 or longs:1,2,3. The assembled bytes are round-tripped through tool 15's parser before they are shown — every field must read back exactly, so a script the parser cannot delimit is refused rather than emitted unverified. Construction only: a box exists on-chain only once a signed transaction creating it is accepted, and this tool signs and sends nothing.

18 · Sigma constant inspector (one register ⇄ its hex)

A box's registers R4–R9 each hold one Sigma constant — a type byte plus the value's bytes — and that is exactly how explorers and node APIs show a register on its own (a babel box's R5 price in tool 12, for example). Until now the only way to read one here was to embed it in a whole box for tool 15. Paste one constant's hex and I decode it locally with the same reader tool 15 uses — the same integer widths too, Short and Int through the 32-bit zigzag, Long through the 64-bit one, so even an SInt at a 32-bit extreme reads back as the value that was written. Or go the other way: enter a typed value in tool 17's register form — bool:true, byte:-5, short:17, int:852574, long:430550309, bigint:1039, group:<66 hex chars>, dlog:<66 hex chars>, bytes:<hex>, ints:1,2,3 or longs:1,2,3 — and I encode it and round-trip the hex through the decoder before showing it. Two honest limits, the same ones tool 15 states: a constant whose type is outside the decoded set (an Option, Box or AvlTree constant), and a SigmaProp that is not the ProveDlog form, stop plainly rather than being guessed at, and trailing bytes after one constant are reported instead of silently ignored.

19 · P2PK ErgoTree builder (public key → ErgoTree)

The one encode direction this hub was missing: tools 8, 10, 11 and 16 go key → address, tree → address, address → tree and tree → P2S, but nothing turned a public key into the ErgoTree itself — the hex explorers and SDKs show for every P2PK box, and the input tools 15, 16 and 17 expect. The standard P2PK tree is a header byte 00 (version 0, no size field, no constant segregation) followed by the ProveDlog proposition — 08 cd — plus your 33-byte compressed public key, exactly the script Ergo builds for a P2PK box and the one tool 11's decoder reverses. The tree itself carries no network, so it is the same on both; the network only picks which addresses I derive alongside it — the P2PK address from tool 8 and the P2SH address from tool 10. The built tree is round-tripped through tool 10's parser and the address through tool 11's decoder before either is shown. Public keys only — never type a private key or seed phrase into any website, this one included.

20 · P2SH address builder (ErgoTree → pay-to-script-hash address)

Tool 10 derives a script's P2SH address as one line of its inspection; this is that derivation as a builder in its own right, with the round-trip check up front. A P2SH address carries only the script hash: a prefix byte (02 mainnet / 12 testnet), then the first 24 bytes of Blake2b-256 over the script's proposition — the ErgoTree without its header byte, and without the VLQ size field when the header carries one — plus the usual checksum. Hashing the full tree bytes instead was a real funds-at-risk bug (fleet-sdk/fleet#219): a node re-derives the hash from the proposition when it checks a spend, so boxes sent to a full-tree-hash address can never be spent. One honest refusal, the same one my fleet fix makes: a constant-segregated tree gets no P2SH address here, because its reference hash needs the constants substituted back in, which raw tree bytes alone cannot reconstruct — tool 16's P2S builder carries those trees exactly instead. The built address is round-tripped through tool 11's decoder before it is shown: it must decode back to this exact script hash.

21 · Blake2b-256 hash calculator (the hash behind box IDs)

One hash sits underneath almost everything on this page: a box ID is the Blake2b-256 of the box's serialized bytes (tool 14), an address checksum is the first 4 bytes of Blake2b-256 over the address prefix and content (tools 2 and 8), and a P2SH script hash is its first 24 bytes over the script's proposition (tools 10 and 20). This tool is that primitive on its own: paste bytes as hex — a box, a script proposition, anything — or type plain text (hashed as its UTF-8 bytes), and get the full 32-byte digest plus the 24-byte hash192 form. Empty input is hashed, not rejected: the digest of zero bytes is a well-defined value. An optional expected digest reports a match or a mismatch plainly. Verified against Python's hashlib before it shipped here. Hashing is not encryption and proves no ownership — it signs and sends nothing.

22 · Base58 codec (the encoding every address is written in)

Every Ergo address on this page is Base58 text over raw bytes — tools 2, 8, 11, 13, 16 and 20 all encode or decode it behind the scenes. This tool is that codec on its own: turn hex bytes into Base58, or a Base58 string back into the exact bytes it carries, leading zero bytes and all (each one is a leading “1”). The alphabet is the one Ergo uses — it has no 0, O, I or l, so those four characters are rejected on decode. This is plain Base58, not Base58Check: it adds no checksum and verifies none — an address decoded here comes out as prefix + content + its stored checksum bytes verbatim, and tool 2 is the one that verifies that checksum. Empty input converts to the empty result, not an error. Verified against an independent Python build before it shipped here. Encoding is not encryption and proves no ownership — it signs and sends nothing.

23 · VLQ codec (how integers are written inside a box)

Almost every integer inside a serialized box is written as a VLQ — a variable-length quantity: the box's value, its creation height, each token amount, the counts and the output index in tools 15 and 17, and the proposition size in a size-flagged ErgoTree (tool 10). The encoding is unsigned LEB128, exactly as fleet-sdk writes it: 7 bits per byte, least-significant group first, the high bit set on every byte except the last — so 0 is 00, 128 is 8001, and the storage-rent period of 1,051,200 blocks is c09440. There is no negative or fractional VLQ. Decode here is strict, the way a box parser must be: the bytes must be exactly one VLQ — a truncated encoding and trailing bytes are refused — and the spelling must be canonical, so an overlong form like 8000 for zero is rejected instead of read as a second spelling of the same number. Exact BigInt maths at any size, verified against fleet-sdk's published VLQ vectors and an independent Python build before it shipped here. Encoding only — it signs and sends nothing.

24 · ZigZag codec (how signed integers are written inside a box)

Tool 23's VLQ has no negatives — so a signed integer is first zig-zagged: 0 → 0, −1 → 1, 1 → 2, −2 → 3, folding the negatives into the odd numbers so small magnitudes of either sign stay small, and only then written as a VLQ. That two-step form is how every signed value inside a box or register is stored — an SLong through the 64-bit zig-zag, an SShort or SInt through fleet-sdk's 32-bit one. Pick the width and go either way here: a signed number to its unsigned zig-zag value and exact VLQ hex, or VLQ hex back to the signed number. The widths genuinely differ, and the extremes show why: 2147483647 zig-zags at 64-bit width to 4294967294 (feffffff0f), but at 32-bit width fleet zig-zags in signed 32-bit space and writes a negative result widened to its unsigned 64-bit form, so the same number comes out as 18446744073709551614 (feffffffffffffffff01) — the exact spelling tools 15, 17 and 18 read and write at the 32-bit extremes. Decode is strict, the way a box parser must be: exactly one canonical VLQ, and re-encoding the decoded value at the chosen width must reproduce the input byte-for-byte, so an over-wide VLQ whose bits the width would truncate or wrap is refused instead of read as a different number. Exact BigInt maths, verified against fleet-sdk's published ZigZag vectors and an independent Python build before it shipped here. Encoding only — it signs and sends nothing.

25 · Box health checker (minimum, rent and age in one verdict)

Tools 3, 5 and 7 each answer one question about a box — here they are answered together. Give me a box's serialized size, the ERG it holds, and its creation and current block heights (all on the box's explorer page), and I check it against the two size-based protocol rules and the rent clock at once: the protocol minimum for its size (serialized bytes × 360 nanoERG per byte, tool 5), one storage-rent payment for its size (bytes × 1,250,000 nanoERG per byte, tool 3), and whether it has reached rent eligibility at creation height + 1,051,200 blocks (tool 7). 26 · Emission & supply calculator (block height → new coins + total issued)

Ergo's issuance is written into the protocol, so any block height has an exact answer. Give me a height and I work it out with the chain's own monetary rules — the monetary settings in the reference node's configuration, run through its EmissionRules: a flat 75 ERG per block below height 525,600, then 3 ERG less every 64,800-block epoch (72, 69, 66, …) until the rate reaches 0 at block 2,080,800 and the full 97,739,925 ERG maximum supply stands issued. 27 · EIP-4 token metadata codec (token name, description, decimals ⇄ issuance registers)

Every Ergo token describes itself in its issuance box, and EIP-4 — the ecosystem's asset standard — fixes the format: R4 holds the token name, R5 the description and R6 the number of decimals, each as a Coll[Byte] constant carrying the UTF-8 text of the value: the byte 0e, a VLQ byte-length, then the bytes. That includes the decimals — EIP-4's own worked example (the "USD" token issued back in block 98,288) encodes 2 decimals as the one-character string "2", hex 0e0132, not as a number; some tokens in the wild do use an Int constant for R6 instead, and my decoder accepts that form too and tells you which one it found. R7 can add a 1–2 byte asset type — NFT picture/audio/video/collection/file-attachments, or a membership token — also as Coll[Byte]. Encode your metadata into the exact register hex an issuance box needs, or paste registers from an explorer to read them back. Everything runs locally on what you type; the token's ID is a separate chain fact (the box ID of the issuing transaction's first input) that no register contains. Registers only — this builds no transaction, signs nothing and mints nothing.

28 · EIP-44 data-hash codec (arbitrary data ⇄ its ADH representation)

Ergo addresses are a prefix byte, some content and a Blake2b-256 checksum, Base58-written — and EIP-44, the ecosystem's proposed arbitrary-data signing standard, points that exact machinery at data instead of a key: it adds address type 4, ADH (arbitrary data hash), whose content is simply the Blake2b-256 hash of your data. The result is a short, checksummed string that stands for the data — for proving ownership or stamping a document, a wallet signs the bytes 00 + network byte + that hash, and the leading 00 matters: a serialized transaction begins with its input count, never 0, so a data signature can never be tricked into doubling as a transaction signature, and the network byte stops a testnet signature replaying on mainnet. Two honest warnings. First, EIP-44 is a proposed standard, not an adopted one — Ergo's spendable address types today are 1 (P2PK), 2 (P2SH) and 3 (P2S), so this string is a data representation for message signing, not a payment address: never send ERG to it. Second, the hash is one-way — decoding a representation gives the hash back, never the original data. Everything runs locally on what you type; this tool holds no keys, signs nothing and sends nothing.

30 · Serialized transaction builder (fields → transaction bytes + ID)

31 · HD address derivation (seed → your wallet's addresses, EIP-3)

Every Ergo wallet address comes from one seed by a fixed recipe, and until now this hub could check addresses but not show where they come from. The recipe is BIP32 with Ergo's EIP-3 path: the master key is HMAC-SHA512 (keyed with the words "Bitcoin seed") over the seed, split into a key and a chain code; each step down the path m/44'/429'/account'/change/index — 429 is Ergo's registered coin type — is another HMAC-SHA512 whose left half is added to the parent key modulo the secp256k1 group order, hardened steps (the ones with a ′) hashing the private key and normal steps hashing the public key, exactly as ergo-wallet's ExtendedSecretKey does it, including its retry-with-the-next-index rule for the astronomically rare invalid child. The last key's public key becomes a P2PK address through tool 8's construction, and every address shown is round-tripped through tool 11's decoder first. Paste a seed as hex — a BIP39 seed is 64 bytes, 128 hex characters; this tool takes no mnemonic words, because turning words into a seed is a wallet's job on a device you trust. Only public keys and addresses are ever displayed — no private key is shown — and the seed is not stored, logged or sent anywhere. Honest warning, in plain words: a seed is the master secret of a whole wallet. Never type a real one into any website, this one included — use a throwaway test seed here, and do real derivation inside your wallet.

32 · Public key inspector (compressed key → the point behind it)

Every P2PK address and ProveDlog script on Ergo carries a compressed secp256k1 public key — 33 bytes: a prefix (02 for even y, 03 for odd y) and an x-coordinate. But the prefix and length are all tools 8 and 19 check, and they are not enough: a compressed key is only a real key if its x names a point actually on the curve, where y² = x³ + 7 modulo the field prime p. Roughly half of all x values have no point at all — x³ + 7 is a quadratic non-residue for them — and any x ≥ p is outside the field entirely; an address formatted around such bytes guards a key nobody can ever hold. This inspector does the real check: because p is 3 modulo 4, a square root of x³ + 7, when one exists, is (x³ + 7)^((p+1)/4) mod p — it recovers y, pins the parity the prefix claims (the other root, p − y, is the point's negation, so the same x under the other prefix is a different, also valid point), re-verifies the curve equation, and re-compresses the point before showing anything. It then shows the full point (x and y), the uncompressed form (04 + x + y), the SGroupElement Sigma constant (07 + the compressed key) that tool 18 reads and writes, and the key's P2PK addresses on both networks, round-tripped through tool 11's decoder. A public key is public — inspecting one proves no ownership of it, and no private key can be found from the point. Public keys only: never type a private key or seed into any website, this one included.

62 · Block header inspector (serialized header bytes → every header field, with the header ID recomputed and checked)

Every other tool here works below the header — boxes, transactions, trees. This one opens the header itself: the ~220 bytes that head every Ergo block, whose Blake2b-256 hash is the block's ID. Paste a serialized block header — the bytes a node or sigma-rust holds for a block, Autolykos solution included — and I walk the reference layout exactly: version byte, parent ID, AD-proofs root, transactions root, the 33-byte state root (the AVL digest carries one extra byte; note the transactions root precedes it on the wire), the timestamp as a VLQ, the extension root, nBits as the header's one fixed-width number (4 big-endian bytes, not a VLQ), the height as a VLQ, the 3 miner-vote bytes, and, for version 2 and up, one length byte for any not-yet-defined extra fields. Then the Autolykos solution: version 1 headers carry miner key, one-time key, nonce and a length-prefixed distance; version 2 and up serialize only miner key and nonce, whatever JSON displays show. The tool returns every field, the difficulty decoded from nBits with the exact compact-bits algorithm, and the header ID recomputed as Blake2b-256 over the full serialized bytes — the reference definition — and if you supply the ID you expect, it is compared. The header is verified before anything is shown: it is located twice, once by the field parser and once by an independent offset-only re-walk, the parsed fields must re-serialize byte-for-byte to the bytes you pasted, and the walk must end exactly at the last byte. The honesty boundary is stated plainly: this recomputes the ID and decodes the fields — it does not verify the Autolykos proof-of-work hit against the difficulty target, and an ID is only a hash of these bytes, not proof the block sits on the main chain; that verdict belongs to a full node. Inspection only: it fetches nothing, signs nothing and sends nothing.
